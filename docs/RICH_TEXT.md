# Rich text, Markdown and LaTeX

Status: implementation started, 2026-10-04. Stage 0 (code and quote
blocks; entities clicks act on and formatted dates, 2026-10-06), stage 1
(reading rich messages, 2026-10-05), stage 2 (the article engine, drawn
in the bubble, 2026-10-06), the engine in the bubble and the article
window with its search, zoom and sharing (stage 3, 2026-10-06), the
drafts bots stream (2026-10-06), formulas by RaTeX (stage 4, 2026-10-06),
stage 4a (code highlighting, 2026-10-05), the `.md` viewer (stage 5,
2026-10-07), Instant View (stage 6, 2026-10-07) and saving as HTML with
copying as HTML (stage 7, 2026-10-07) are implemented: the plan is done;
see "Implementation progress" below.
The research notes gather what Telegram sends, how Telegram Desktop shows
it, what KomaruGram has, and a
measured comparison of the libraries the work needs: a Markdown parser
(goldmark or cmark-gfm), a LaTeX renderer (MicroTeX, star-tex, go-latex or
RaTeX) and a code highlighter. Choosing a library is the maintainer's
decision (AGENTS.md).

Decided (2026-10-04):

- **LaTeX: RaTeX**, built for `wasm32-wasip1` and run in wazero's compiler.
  (Built for `wasm32-unknown-unknown` in the end: the export crate needs
  nothing of WASI, and so the module imports nothing; see stage 4.)
- **Code highlighting:** the Go port of libprisma's tokenizer on regexp2
  v1.12.0, with grammars generated by our own copy of libprisma's
  generator.

- **Markdown: cmark-gfm in wasm** (2026-10-07), desktop-app's fork that
  Telegram Desktop builds, as recommended below.

Telegram Desktop is GPLv3: port its behavior, not its code (the rules in
[PLAN.md](PLAN.md)). The reference is a local `tdesktop/` clone of 7.2.10
beta (2026-09-25, layer 229). Paths below are relative to
`tdesktop/Telegram/SourceFiles/`.

## What Telegram sends

### Rich messages

Layer 229 (`mtproto/scheme/api.tl`):

```
message … rich_message:flags2.13?RichMessage = Message;
richMessage#baf39d8b flags:# rtl:flags.0?true part:flags.1?true
    blocks:Vector<PageBlock> photos:Vector<Photo> documents:Vector<Document> = RichMessage;
messages.getRichMessage#501569cf peer:InputPeer id:int = messages.Messages;
```

The same `rich_message` field is in `draftMessage`, `ephemeralMessage` and
`botInlineMessageRichMessage`.

- **Blocks.** `PageBlock` has these constructors: title, subtitle, author
  and date, header, subheader, heading 1–6, kicker, paragraph,
  preformatted (with a language), footer, divider, anchor. Then lists:
  `pageBlockList` and `pageBlockOrderedList` with text or nested blocks, a
  checkbox, `checked`, an explicit `num`/`value`, and an ordered `type`.
  Then quotes: blockquote (with `collapsed`), blockquote with blocks, and
  pullquote. Then media: photo, video, audio and document, each with a
  caption, plus collage, slideshow, cover and map. Then embed, embed post,
  channel and related articles. Then a table (bordered, striped, compact;
  cells with colspan, rowspan and alignment). Then details (`open`), math,
  thinking and button row. Media is referenced by ID and resolved from
  `richMessage.photos` and `documents`.
- **Inline text.** `RichText` is a tree: plain text, bold, italic,
  underline, strike, fixed, link (`textUrl` with `webpage_id`), email,
  phone, sub- and superscript, marked, spoiler, anchor, inline image
  (`textImage`), custom emoji, mention, mention by user ID, hashtag, bot
  command, cashtag, the auto-detected url, email and phone, bank card, date
  (`textDate` with format flags), diff, button (`textButton`) and math
  (`textMath`).
- **Formulas arrive as LaTeX source**, `textMath.source` and
  `pageBlockMath.source`. The client typesets them. This is why a LaTeX
  renderer is needed for rich messages and not only for `.md` files.
- **Markdown and HTML are parsed by the server.** Bots and clients send
  `inputRichMessageMarkdown` or `inputRichMessageHTML`, and every client
  receives blocks. A Markdown parser is needed only for the `.md` viewer,
  and later for pasting into an editor.
- **`part`.** A long message arrives cut short. tdesktop shows the part in
  the bubble with a "View full article" button
  (`lng_view_button_full_article`,
  `history/view/history_view_view_button.cpp`). The button opens the IV
  window, which loads the whole message with `messages.getRichMessage`
  (`iv/iv_instance.cpp:1274`). The same happens for an anchor or a footnote
  that is not in the part. The call only reads, so it is allowed on a
  developer's account.
- **The message's text.** tdesktop sets the item's text to
  `FlattenRichPageSummary(page)`, which the chat list, replies,
  notifications and search use. It sends a rich message with an **empty**
  `message` string (`MTP_string(QString())` in `ApiWrap::sendRichMessage`,
  `apiwrap.cpp:4694`). KomaruGram shows rich messages today as "Пустое
  сообщение" (an empty message), as the maintainer saw on a live account
  (2026-10-04). So `message.message` evidently arrives empty, as tdesktop
  sends it.
- **Ticking a checklist item edits the message**
  (`api/api_rich_tasks.cpp` through `api_editing`). It is a write: try it
  only in `-demo`.

Limits from the Bot API ("Rich Message Limits",
<https://core.telegram.org/bots/api#rich-message-limits>): up to 32,768
UTF-8 characters, counting custom emoji alternative text and formula
source. Up to 500 blocks, nested ones included. Up to 16 levels of nesting.
Up to 50 media. Up to 20 table columns.

### Telegram's Markdown dialect

The Bot API's "Rich Markdown style"
(<https://core.telegram.org/bots/api#rich-markdown-style>) is GFM plus the
following:

- `==marked==` and `||spoiler||`;
- `$inline$`, `$$display$$` and fenced ` ```math ` formulas;
- footnotes (`[^id]`);
- `<details open><summary>`;
- `<u>`, `<ins>`, `<sub>` and `<sup>`;
- Telegram's tags: `<tg-spoiler>`, `<tg-emoji>`, `<tg-time>`, `<tg-math>`,
  `<tg-map>`, `<tg-collage>`, `<tg-slideshow>`, `<tg-button>` and
  `<tg-button-row>`;
- `tg://emoji?id=`, `tg://time?unix=` and `tg://user?id=` links.

The `.md` viewer does not have to accept all of this. Formulas, marks and
spoilers are worth supporting so that a file a bot produced looks the same
as the bot's message.

## How tdesktop parses and draws

- **Markdown parser: cmark-gfm.** It comes from the `desktop-app` fork, on
  the `tdesktop` branch, which carries three hardening commits from August
  2026 over upstream. tdesktop enables the extensions `table`,
  `strikethrough`, `autolink`, `tagfilter` and `tasklist`, and the options
  `SOURCEPOS`, `FOOTNOTES` and `STRIKETHROUGH_DOUBLE_TILDE`
  (`iv/markdown/iv_markdown_parse_convert.cpp:709`,
  `iv/markdown/iv_markdown_parse_finalize.cpp:755`). It parses under a
  counting allocator with an abort flag. The limits
  (`iv/markdown/iv_markdown_parse.cpp`): a 4 MB source, 100,000 cmark
  nodes, nesting up to 128, 64 KB per formula, 10,000 formulas. Formulas are
  found by its own scanner before cmark runs
  (`iv/markdown/iv_markdown_math.cpp`).
- **Prepare limits** (`iv/markdown/iv_markdown_prepare.cpp:82`):
  - rich message tables: 128 rows, 20 columns, 1,024 cells;
  - Markdown tables: 1,000 rows, 50 columns, 50,000 cells;
  - list and quote depth: 16;
  - 4,096 prepared blocks.
- **Math: MicroTeX,** from the `desktop-app` fork
  (`iv/markdown/iv_markdown_microtex.cpp`). The fork carries 27 commits over
  NanoMichael/MicroTeX: TeX fonts bundled as Qt resources, tinyxml2
  removed, and many fixes for crashes on malformed input.
- **Code highlighting: libprisma** (desktop-app fork of
  TelegramMessenger/libprisma, MIT).
- **When a `.md` file cannot be shown,** tdesktop says "Can't preview this
  Markdown file" and offers "Open file" (`lng_markdown_preview_cant`,
  `lng_markdown_preview_open_file`).

## What KomaruGram has

- **Message entities.**
  - `tgstore/convert.go` turns them into `model.Entity`, and
    `model.TextRuns` splits the text into styled runs.
  - `chatPage.richText` (`ui/history_text_blocks.go`) draws the runs as flows
    through `internal/messenger/styledtext`.
  - Done: bold, italic, underline and strike; spoiler with its reveal;
    links and `@mentions`; mentions by ID, as `tg://user?id=…` links that
    the client opens itself (`model/tglink.go`); custom emoji; text
    selection.
  - Inline `code` is monospace. `pre` has a block, language header and
    copy button. A blockquote has a bar; `collapsed` shows three visual
    lines and can be expanded locally. Both retain nested inline styles,
    source offsets and selection across blocks.
  - Hashtags, cashtags, bot commands, email, phone and bank card numbers
    act on a click, and formatted dates are written in the reader's
    language (stage 0, below). Dropped as `unsupported`, shown as plain
    text: the diff entities and `messageEntityBox`.
- **`rich_message` is read** (stage 1): `tgstore/rich.go` converts it into
  `model.RichPage`, and the message's text is the page's summary
  (`model/rich_summary.go`), for the chat list, replies and search. The
  bubble draws the page as an article (stage 2).
- **A `.md` file opens in the system's program** (`ui/attachments.go`).
- **No Instant View, no Markdown parser, no math.** goldmark is in `go.sum`
  only because gotd's tooling (ogen) needs it; it is not linked into the
  binary.
- **Precedent for C libraries:** `pkg/drdec`, `pkg/vp9`, `pkg/opus` and
  `pkg/lottie` embed MIT/BSD code compiled to `wasm32-wasip1`. A build
  script sits beside each, and the module runs in wazero under
  `pkg/sandbox`'s memory and time limits. LGPL and patent-encumbered
  modules are fetched instead (`internal/messenger/wasmmodule`).

## Markdown parser: goldmark or cmark-gfm

The parser is needed only for `.md` files, and those come from strangers.
What matters most:

- how it behaves on hostile input;
- whether a runaway parse can be stopped;
- whether the dialect matches tdesktop.

Speed on ordinary documents is about the same for all of them.

### Candidates

| | goldmark v1.8.6 | goldmark v2.1.6 | cmark-gfm (wasm) |
|---|---|---|---|
| Language | Go, only the standard library | Go, only the standard library | C (BSD-2-Clause, parts MIT), compiled to wasm |
| Spec | CommonMark 0.31.2 + GFM tables, strikethrough, task lists, linkify, footnotes, definition lists | same; AST rebuilt with generics, every node has a start position | CommonMark + GFM: table, strikethrough, autolink, tagfilter, tasklist, footnotes |
| Status | maintained (v1.8.6, 2026-09-03) | released 2026-08-27; README: "v2 is still in the early stages of release" | upstream master fixed 2026-09-22; last tagged release 0.29.0.gfm.13 (2023-07) |
| Security record | one XSS in the HTML renderer (GO-2026-5320), which this use does not involve | same code base | 10 advisories 2020–2023: DoS through quadratic complexity, and one heap corruption in the table extension (CVE-2022-24724); all fixed |
| Telegram's extras (`==`, `\|\|`, `$…$`) | Go inline parsers, easy | Go inline parsers, easy | C syntax extensions, or a scan in Go before parsing (as tdesktop does for math) |
| How the AST reaches Go | directly | directly | serialized by a C shim, decoded in Go |
| Same behavior as tdesktop | no | no | yes, same parser and options |
| Stopping a runaway parse | impossible: `Parse` takes no context, and its goroutine cannot be killed | same | sandbox memory cap (a trap); time checked after the call, or wazero's interrupt for this one module |
| Memory | uncapped, in the client's heap | uncapped | capped per sandbox |

### Measurements

Linux amd64, Go 1.26.5, clang 22, wasi-sdk 34 (sysroot and compiler-rt),
wazero 1.12.0. goldmark: parse plus an AST walk, with GFM and footnotes.
cmark-gfm native: the `cmark-gfm` CLI with tdesktop's extensions, rendering
XML (so a little more work than parsing). cmark-gfm wasm: the `tdesktop`
branch, built as a reactor with a shim that parses and renders XML, run in
wazero with a 256 MB cap, a fresh instance per input. Times are wall clock,
one run each.

What this shows:

- **cmark-gfm stayed linear on every hostile input tried.** These are the
  2023 CVE fixes at work. Its one weakness, memory on a huge table, is a
  contained trap in the sandbox. tdesktop handles it with a node budget.
- **goldmark has superlinear paths in both versions,** and v2 brought a new
  one in emphasis that v1 does not have. A 1 MB file can occupy a core for
  a minute. Nothing can stop the parse, and memory is not capped. Using
  goldmark would need a low size limit (the link case already takes
  0.5–1 s at 100 KB), upstream fixes or local patches, and a goroutine that
  is allowed to run to its end. These cases are recorded here, not
  reported upstream.
- Ordinary documents parse in under 0.1 s in all of them. The wasm build is
  about 4× slower than native, which does not matter at these sizes.

### Recommendation

**cmark-gfm in wasm**, built like `pkg/drdec`:

- the `desktop-app` fork's `tdesktop` branch;
- a C shim that serializes the AST compactly;
- Telegram's extras found by a pre-scan in Go, as tdesktop does for math;
- tdesktop's limits: 4 MB, 100k nodes, nesting 128.

It matches tdesktop's behavior, its bad cases are contained, and it adds
about 0.3 MB.

goldmark is the simpler choice: pure Go, extensible in Go, nothing to build.
It is acceptable if the size limit is low and the quadratic cases are fixed
first.

## LaTeX renderer

Rich messages carry formulas as LaTeX source, and Telegram's clients render
the KaTeX-like subset: `\frac`, `\sqrt`, sub- and superscripts,
`\left…\right`, `\begin{pmatrix}`, `\text`, `\mathbb`, Greek letters and
operators. Fifteen formulas were tried with each candidate: ordinary ones;
malformed ones (`\frac{1}{`, `}}}}`, an undefined command); `\text` with
Cyrillic; fractions nested 200 deep and `\sqrt` nested 1,000 deep; 3,000
nested superscripts; and recursive macros (`\def\a{\a}\a` and
`\newcommand{\b}{\b\b}\b`).

### Candidates

| | MicroTeX (desktop-app fork) in wasm | star-tex | go-latex |
|---|---|---|---|
| What it is | C++17 port of JLaTeXMath: a LaTeX math typesetter | Knuth's TeX: `modernc.org/knuth` (tex.web translated to Go) with DVI, TFM, PK and Type1 tools | A small mathtext renderer in Go, like matplotlib's |
| License | MIT; fonts below | BSD-3-Clause; fonts: CM and AMS (Knuth's and OFL) | BSD-3-Clause |
| Status | upstream last pushed 2024-08; the fork is maintained by tdesktop (2026-08) | v0.7.1, 2025-04-12 | GitHub repository archived; v0.3.0 on Codeberg, 2026-05 |
| Syntax | LaTeX math (`\frac`, environments, `\text`, `\mathbb`…) | plain TeX only: `\frac` and `\begin` stop with "Emergency stop" | a fragment; panics on `x^2` (`unknown ast node *ast.Sup`), `\left`, `\begin`, `\text` and `\mathbb` |
| Size | module 1,560,252 B (371,359 B gzipped) + TTF fonts 1.3 MB | +4,869,792 B in the stripped messenger (engine and fonts) | not measured |

### MicroTeX in wazero

All 76 source files of the fork's core (without `platform/` and `samples/`)
build for `wasm32-wasip1` with clang 22 and wasi-sdk 34. Two things are
needed for that build:

- the exception-handling libc++ (`-fwasm-exceptions`, headers in
  `include/wasm32-wasip1/eh/c++/v1`, libraries in `lib/wasm32-wasip1/eh`);
- the new exception encoding (`-mllvm -wasm-use-legacy-eh=false`), because
  wazero refuses legacy exception instructions.

wazero 1.12 supports exceptions as an experimental feature
(`experimental.CoreFeaturesExceptionHandling`).

With font and layout stubs in place of the three host functions:

- **The interpreter** (`wazero.NewRuntimeConfigInterpreter`) rendered all
  15 formulas. Malformed ones came back as caught errors. Instantiation
  took 94 ms and `initBundled` 11 ms.
- **The compiler** fails with `invalid table access` in `__dynamic_cast`
  under `__gxx_personality_wasm0`. It happens when MicroTeX catches the
  exception it throws while parsing `\infty`. A minimal C++ test passes in
  both modes: derived, base, `std::` and `int` exceptions, and a rethrow
  across two `try` blocks. So the fault is in wazero's compiled exception
  path on a larger module. It is recorded here, not reported to wazero.
  Until it is fixed, MicroTeX would run under the interpreter. Formulas are
  small and can be cached as drawn, so the speed is acceptable.
- **Exceptions are expensive under wazero's compiler even where they
  work.** This was measured on libprisma (see "Code highlighting"): the same
  code with `-fwasm-exceptions` ran 45–105 times slower compiled than
  without exceptions. Every `try` costs, thrown or not. Under the
  interpreter the difference vanishes, but the interpreter is 30–45 times
  slower than compiled code. A fixed compiler bug would therefore not make
  MicroTeX fast. Only a build without exceptions would, and MicroTeX
  depends on them.

Without exceptions (`-fno-exceptions`) it is not usable. MicroTeX throws in
129 places, some of them in ordinary parsing, as for `\infty`.

Fonts: the fork bundles 46 TTFs.

- The base fonts (`res/fonts`: Computer Modern, Euler, AMS symbols,
  `dsrom`, `rsfs`) are under Knuth's license, OFL and the `dsrom` license.
- **`res/cyrillic` and `res/greek` are GPLv3.** tdesktop is GPLv3 itself and
  bundles them. KomaruGram is Unlicense/MIT. **They are not needed:**
  - Their registrations point at XML files
    (`cyrillic/language_cyrillic.xml`), and the fork removed the XML
    loaders.
  - In the drawing prototype below, Cyrillic in math mode (`v_{ср}`,
    `Ж + щ = ё`) went to `TextLayout`, the host's font.
  - Unicode Greek (`α + β = Γ`) went to `cmmi10` and `cmr10`, the same as
    `\alpha + \beta = \Gamma`.
  - Neither ever asked for a file in `res/cyrillic` or `res/greek`.
  - What is needed is `res/fonts` alone: 30 files, 462,328 bytes (267,168
    gzipped). The GPL alphabets would add 779,316 bytes.

### Drawing prototype

A recording backend replaces the three host functions and `Graphics2D`, in
about 230 lines of C++ in the module:

- fonts are names;
- `drawChar`, `drawText`, `drawLine`, `drawRect` and `fillRect` become
  operations in absolute coordinates, with the current affine matrix and
  color;
- `TextLayout`'s bounds come from a host import, `measure_text`.

The Go side draws the operations:

- TTF outlines with `golang.org/x/image/font/sfnt`, loaded at 256 times the
  size and scaled down, so that the 26.6 fixed point keeps its precision;
- the outlines filled with `golang.org/x/image/vector`;
- the host's font for `\text` (Go fonts in the prototype).

`x/image` is already a dependency. The module with this backend is
1,625,234 bytes.

Fourteen formulas were rendered to PNG and looked over: powers, an
integral, a sum, `pmatrix`, `cases`, `\left(…\right)`, `\sqrt[3]`,
`\mathbb`, `\mathcal`, `\mathfrak`, `\vec`, `\hat`, `\bar`, `\lim`,
`\overbrace`, `\boxed`, and `\text{Скорость}` beside math. All came out
with TeX's spacing and Computer Modern glyphs; no glyph failed to map. Each
took 2–8 ms under the interpreter, the unclosed `\frac{1}{` included. They
used six font files: `cmmi10`, `cmr10`, `cmsy10`, `cmex10`, `msbm10` and
`eufm10`.

Two mistakes in the first version of the prototype, both on the Go side,
are worth keeping in mind for the real one:

- **Stroke width is in the transformed space.** MicroTeX draws at a scale
  of 20 and gives a fraction bar a width of 0.04. A minimum width clamped
  before the transform drew fraction bars as black squares.
- **`TeXRender::getHeight()` already includes the depth.**

### Telegram for Android

Telegram for Android draws formulas with **JLaTeXMath**, the Java library
MicroTeX was ported from (`TMessagesProj/lib/jlatexmath`,
`ui/Components/LatexInliner.java`, `ui/iv/Latex.java`). So both official
clients draw formulas with the same family of engines, which is an argument
for MicroTeX where looking like Telegram matters.

### Rust libraries, for reference

Rust builds to `wasm32-wasip1` without C++ exceptions: a panic aborts, and
the abort is a trap that the sandbox contains. A Rust module would
therefore run in wazero's **compiler**, not the interpreter that MicroTeX
needs. `pkg/lottie`'s tlottie is a precedent.

RaTeX was built and measured (below). The others come from crates.io,
GitHub and their sources.

| Library | What it does | Status | Fit |
|---|---|---|---|
| **RaTeX** (`erweixin/RaTeX`, crates `ratex-*` 0.1.14) | A KaTeX-compatible math typesetter in Rust: lexer, parser (13,576 lines), layout (12,181 lines) and a **display list**. Exporters for SVG, PDF, PNG (tiny-skia), Cairo and GTK4; a C ABI; JNI; wasm-bindgen | MIT, KaTeX fonts under OFL 1.1; 1,512 stars; pushed 2026-09-25; first crate 2026-03 | **The one serious candidate** |
| katex-rs (`katex-rs/katex-rs` 0.3.0) | KaTeX re-implemented in Rust, tracking KaTeX 0.18.5 | MIT; 55 stars; pushed 2026-09-30 | No: outputs HTML and MathML, which need a browser to lay out |
| Typst with mitex | mitex converts LaTeX to Typst; Typst typesets it | Apache-2.0; active | No: a whole typesetting system to draw a formula |
| ReX (`ReTeX/ReX`) | Math typesetting with OpenType MATH fonts | 137 stars; last push 2020-07 | No: abandoned |
| `katex` 0.4.6, `math2img` | KaTeX or MathJax run in an embedded JavaScript engine | — | No: a JavaScript engine in the client |
| `pulldown-latex`, `latex2mathml`, `math-core`, `lo_math` | LaTeX to MathML | — | No: MathML still has to be laid out and drawn |

What RaTeX offers, read from its sources:

- **Output in our shape.** `DisplayItem` is `GlyphPath` (x, y, scale, font
  name, character code, color), `Line` (with thickness, optionally dashed),
  `Rect` and `Path` (move, line, curve commands; fill or stroke). That is
  the same shape as the MicroTeX prototype's operations above, so the same
  Go drawing code serves both.
- **An entry point we could use.** `ratex-ffi` exports
  `ratex_parse_and_layout(latex, options)`, which returns the display list
  as JSON, plus `ratex_free_display_list` and `ratex_get_last_error`. Built
  for `wasm32-wasip1` as a reactor, it would be called like our other
  modules. The existing `ratex-wasm` targets browsers through wasm-bindgen
  and is no use to wazero.
- **Guards.** The macro expander stops after `max_expand: 1000` expansions,
  as KaTeX does, and the parser has recursion limits. The release profile
  sets `panic = "abort"`. The repository has 556 `#[test]` functions in 52
  files and golden images, but no fuzzing directory.
- **Dependencies.** `serde`, `serde_json`, `phf`, `thiserror`,
  `unicode-normalization`, and three regex crates in the parser: `regex`,
  `regex-lite` and `fancy-regex`, which backtracks. Fonts are embedded
  through `rust-embed` when wanted.
- **Fonts.** 20 KaTeX TTFs, 513,664 bytes (266,820 gzipped), under the SIL
  OFL 1.1. Their notice has to ship with the client.
- **Syntax.** KaTeX's, plus mhchem's `\ce` and `\pu` and bussproofs proof
  trees. Missing: `\includegraphics`, and the HTML extensions only in part.

**Compared with MicroTeX:**

- RaTeX would run compiled, so it would be fast.
- It is maintained and needs no C++ toolchain.
- It understands KaTeX's syntax, which bots that write Rich Markdown are
  likely to target.
- Against it: it looks like KaTeX, not like tdesktop and Telegram for
  Android.
- And it is new: its crates appeared in March 2026.

### RaTeX measured

Built with rustc 1.99.0 for `wasm32-wasip1` (toolchain installed with
rustup into a scratch directory). A thin crate over `ratex-parser`,
`ratex-layout` and `ratex-types` exports a reactor:

- `rt_alloc` and `rt_free`;
- `rt_layout(text, display)`, which returns the display list as JSON or a
  parse error;
- `rt_out_len`.

About 50 lines of Rust. The release profile is RaTeX's own: LTO, one
codegen unit, `panic = "abort"`. The module needs no fonts: metrics are
compiled into `ratex-font`. The TTFs are needed only on the Go side, for
outlines.

**Size:**

| Build | Module | Gzipped | wazero compile |
|---|---|---|---|
| `opt-level = 3` | 2,637,341 B | 828,463 B | 1.1 s |
| `opt-level = "z"` | 2,083,734 B | 661,070 B | 0.5 s |
| MicroTeX, for comparison | 1,625,234 B (with the recording backend) | 371,359 B (core) | — (interpreter) |

The regex crates and Unicode tables are the likely difference. That was not
broken down.

**Speed** (`opt-level = 3`):

| Input | wazero compiler | wazero interpreter | MicroTeX, interpreter |
|---|---|---|---|
| The 14 ordinary formulas | 0.08–0.45 ms each (first call 1.2 ms) | 3–17 ms | 2–8 ms |
| 100 × 100 `matrix` | 96 ms | 1.8 s | — |
| `x+` × 16,000 (32,000 characters) | 56 ms | 3.0 s | — |
| `\ce{H2SO4 + 2NaOH -> …}` | 13 ms | 677 ms | — |

`opt-level = "z"` ran 1.4–2 times slower in the compiler.
`WithCloseOnContextDone` made calls about 2–4 times slower, as with
libprisma.

**Hostile formulas,** 20 of them, all bounded. None trapped and none hung:

- 200 nested `\frac`, 1,000 nested `\sqrt`, 3,000 nested superscripts, 500
  nested `\left(` and 300 nested `\overset` all stop with "Recursion limit
  exceeded";
- `\def\a{\a}\a`, `\def\a{\a\a}\a` and `\newcommand{\b}{\b\b}\b` stop
  with "Too many expansions";
- `\undefinedcommand`, `}}}}`, `\includegraphics` and the unclosed
  `\frac{1}{` are parse errors. MicroTeX draws what it can of the last one;
- `\href{javascript:…}` and `\url{file:…}` only lay out text. Opening
  links is the host's business;
- `\rule{100000em}{100000em}`, `\hspace{1000000em}` and `\kern999999em`
  come back as display lists of that size. **The host must bound the size
  it draws.**

After the ordinary formulas the instance's linear memory was 2.2 MB, and
after the hostile set 36 MB. wasm memory never shrinks, so drop the
instance after a large formula, as `pkg/sandbox` does for other modules.

**Drawing.** The Go side of the MicroTeX prototype drew the display list
with small changes:

- coordinates are in em;
- a `GlyphPath` names a KaTeX font (`Main-Regular` → `KaTeX_Main-Regular.ttf`)
  and a character code, at `em × scale`;
- a `Line` is centred on `y`;
- a `Path` holds `{"type": "MoveTo" | "LineTo" | "CubicTo" | "QuadTo" |
  "Close", …}` commands relative to its `x` and `y`;
- characters from the Mathematical Alphanumeric Symbols block map back to
  ASCII in the fonts whose cmap uses ASCII (`katex_ttf_glyph_char`).

The same 14 formulas, looked over as PNGs, came out in KaTeX's style:
`pmatrix`, `cases`, `\sqrt[3]`, `\mathbb`, `\mathcal`, `\mathfrak`,
`\vec`, `\overbrace` and `\boxed` all correct. They used eight of the 20
fonts: `Main-Regular`, `Math-Italic`, `AMS-Regular`, `Caligraphic-Regular`,
`Fraktur-Regular`, `Size2`, `Size3` and `Size4`.

**Cyrillic is the host's job.** `\text{Скорость}` comes back as
`GlyphPath`s in `Main-Regular`, and KaTeX's fonts have no Cyrillic: 10
glyphs had no outline. In a browser KaTeX falls back to the page's font;
here the host has to, with the client's own font. MicroTeX does this
itself, through `TextLayout`.

**Compilation cache.** wazero's `NewCompilationCacheWithDir` cut the
1.1 s compile to 25–31 ms on later runs, with an 8 MB cache. `pkg/sandbox`
now has a cache for every module (`pkg/sandbox/cache.go`):

- **In memory,** shared by the runtimes of a process.
- **On disk,** with every entry signed with HMAC-SHA256. The key is kept in
  the configuration directory, apart from the cache.

A RaTeX module only has to compile through `sandbox.Runtime.CompileModule`
to use it.

### Decision: RaTeX (2026-10-04)

The maintainer chose **RaTeX**, in a module of our own over `ratex-parser`,
`ratex-layout` and `ratex-types` for `wasm32-wasip1`, run in wazero's
compiler. What it takes:

- **The module and its build script.** As `pkg/lottie` holds tlottie (also
  Rust), keep RaTeX at a pinned commit, with the thin export crate and a
  script that builds it. Licenses, from `cargo metadata` for
  `wasm32-wasip1`: RaTeX's crates are MIT. Of the other packages, 19 are
  MIT OR Apache-2.0 and 2 are Apache-2.0 OR MIT; the rest are Unlicense OR
  MIT (`aho-corasick`, `memchr`), Zlib OR Apache-2.0 OR MIT (`tinyvec`),
  and (MIT OR Apache-2.0) AND Unicode-3.0 (`unicode-ident`, used while
  building). All permit embedding. Measure `opt-level = 3` against
  `"z"` on the client's real formulas before settling the size.
- **The KaTeX fonts**, 20 TTFs (267 KB gzipped) under the SIL OFL 1.1,
  embedded on the Go side with their notice, listed in
  [THIRD_PARTY_LICENSES.md](THIRD_PARTY_LICENSES.md).
- **A Go drawer of the display list** with Gio: glyph outlines from the
  KaTeX TTFs into `clip.Path`, lines, rectangles and paths, in em times the
  text size. The prototype's `x/image` drawer is the reference.
- **The host's own duties.**
  - Characters the KaTeX fonts lack, Cyrillic first, are drawn with the
    client's text font.
  - The drawn size is bounded (`\rule{100000em}…` is valid).
  - Links in `\href` and `\url` open only through the client's usual link
    confirmation.
- **The sandbox.**
  - A memory cap, with a fresh instance after a large formula (linear
    memory reached 36 MB on the hostile set).
  - Calls checked after the fact, as `pkg/sandbox` does; every hostile
    formula stayed bounded.
  - The compilation cache every module shares (`pkg/sandbox/cache.go`).
- **Errors.** Show the formula's source, as tdesktop does when a formula
  fails.

What was weighed against it: MicroTeX looks like tdesktop and Telegram for
Android (JLaTeXMath), and its module is smaller. But it runs only in the
interpreter, 10–30 times slower, and needs a C++ toolchain with
exceptions.

### MicroTeX, not chosen

**MicroTeX in wasm** has the same syntax and the same output as tdesktop,
and malformed or endless formulas stay inside the sandbox. It would need:

- a Go backend that draws its ops with Gio. The prototype draws them with
  `x/image`; in the client the same outlines go to `clip.Path`;
- only the freely licensed `res/fonts`, since the GPLv3 alphabets are not
  used;
- the interpreter, or a fix in wazero's compiler.

**RaTeX, as measured.** It is 10–30 times faster, since it runs in
wazero's compiler (with a compilation cache, its compile cost is gone
after the first run). It needs no C++ toolchain. It is maintained, speaks
KaTeX's syntax and mhchem, and every hostile formula was bounded. Against
it:

- it looks like KaTeX, not like tdesktop and Telegram for Android
  (JLaTeXMath);
- its module is larger (661 KB gzipped against 371 KB);
- the host must supply Cyrillic and bound huge sizes;
- it is six months old.

Both give the same kind of display list, so the Go drawing code would not
have depended on the choice. It came down to "looks like Telegram"
(MicroTeX) against "fast, current, KaTeX" (RaTeX), and RaTeX was chosen.

star-tex is real TeX and is pure Go, but it would need a macro layer that
turns LaTeX math into plain TeX, with AMS fonts for `\mathbb`. It would
also need a filter for `\openout`, `\input`, `\read` and `\write`, and a
way to stop endless input; in-process, a parse cannot be stopped. Its
original limits (a 500-character line buffer, 30,001 words of main memory)
reject ordinary long formulas: 1,000 nested roots fail with "TeX capacity
exceeded".

go-latex is not usable for Telegram's formulas.

Until the RaTeX module is in the client, show a formula's source as text.
When a formula fails, tdesktop also shows its source, or `[math]` when the
source is empty (`FallbackText`, `iv/markdown/iv_markdown_math_renderer.cpp`).

## Code highlighting

Code arrives in three places:

- a message's `pre` entity, whose `language` KomaruGram drops today
  (`tgstore/convert.go`);
- a rich message's `pageBlockPreformatted.language`;
- a fenced block in a `.md` file.

Highlighting needs no network and changes nothing on the server. What it
costs is CPU on text from strangers.

### What Telegram's clients do

Both official clients use **Prism.js grammars**. A client that uses the
same grammars colors code the way they do.

- **Telegram Desktop: libprisma.**
  - Where: `desktop-app/libprisma`, a fork of `TelegramMessenger/libprisma`
    (MIT), built by `cmake/lib_prisma.cmake`.
  - What it is: a C++ port of Prism's tokenizer on Boost.Regex.
    `grammars.dat` is generated from `prismjs` 1.29.0: 3,958 patterns, 935
    grammars, 390 language names and aliases (288 languages in its README).
  - Integration: `lib_spellcheck/spellcheck/spellcheck_highlight_syntax.cpp`,
    in the separate `desktop-app/lib_spellcheck` repository, which the
    local clone leaves empty.
    - It highlights a `pre` entity with a non-empty language, and the code
      blocks of IV and Markdown articles (`iv/markdown/iv_markdown_article.cpp`).
    - It runs on one background queue, with an LRU cache of 256 results
      keyed by xxHash64 of the text and the language.
    - The language is lowercased. Its only aliases are `diff` and `patch`
      to `git`.
    - There is no size limit. When token lengths do not add up to the
      text, it drops the colors and logs an error.
  - Colors: the token's `type()` (its `alias()` is ignored) maps to 8
    classes, drawn with the statistics chart palette (`SyntaxHighlightColors`,
    `ui/chat/chat_style.cpp`):

    | Class | Prism token types | Color |
    |---|---|---|
    | 1 | comment, block-comment, prolog, doctype, cdata | `statisticsChartLineLightblue` |
    | 2 | punctuation | `statisticsChartLineRed` |
    | 3 | property, tag, boolean, number, constant, symbol, deleted | `statisticsChartLineRed` |
    | 4 | selector, attr-name, string, char, builtin | `statisticsChartLineOrange` |
    | 5 | operator, entity, url | `statisticsChartLineRed` |
    | 6 | atrule, attr-value, keyword, function | `statisticsChartLineBlue` |
    | 7 | class-name | `statisticsChartLinePurple` |
    | 8 | inserted | `statisticsChartLineGreen` |

    These 27 types cover 58% of the 5,693 token rules in `grammars.dat`.
    Among those left plain are `variable`, `interpolation`, `regex`,
    `parameter` and `namespace`. Also left plain are tokens whose Prism
    alias is colored, such as `doc-comment` (an alias of `comment`) and
    `template-string` (an alias of `string`).
- **Telegram for Android: its own port.**
  - Code: `org/telegram/messenger/CodeHighlighting.java` ports the same
    Prism algorithm to Java with `java.util.regex`.
  - Grammars: in `assets/codelng.gzip`, with grammar nesting limited to
    depth 20.
  - It runs on `Utilities.searchQueue`.
  - Colors: 7 groups with theme keys, defaults in `ThemeColors.java`:
    - `code_keyword` `#E05356`;
    - `code_operator` `#4DBBFF`;
    - `code_constant` `#7F79F3`;
    - `code_string` `#37C123`;
    - `code_number` `#327FE5`;
    - `code_comment` 50% black;
    - `code_function` `#F28C39`.
  - Code is drawn smaller as it gets longer (`getTextSizeDecrement`).

|---|---|---|
| Go port vs libprisma, both on the shipped `grammars.dat` | 2,562 of 2,574 | 12, all on non-ASCII text |
| libprisma vs Prism.js | 2,477 | 97: 76 from languages left out of `grammars.dat`, 11 on non-ASCII text, 10 on ASCII |
| Go port on our own grammars (below) vs Prism.js | 2,559 | 15: 10 on ASCII, 3 BQN, 2 Stata |

**On ASCII the Go port is libprisma, exactly.** Where both differ from
Prism.js, they differ in the same 10 tests. The generator loses those
constructs: HTML's `<!DOCTYPE>` comes out as one token without its inner
tokens, plus some of `maxscript`, `mermaid`, `stata` and `uri`.

**The generator narrows Unicode to Latin-1.** `generate.js:200` replaces
every `\uFFFF` with `\xFF`, a workaround for Boost matching over UTF-8
bytes. JavaScript's identifier pattern `[_$a-zA-Z\xA0-\uFFFF]` thus
becomes `[_$a-zA-Z\xA0-\xFF]` in all 148 places. libprisma then matches
any byte from `0xA0` to `0xFF`, which includes some of the continuation
bytes of Cyrillic letters but not others. In tdesktop, the JavaScript line
`const приветствие = (имя) => …` colors **`вие`**, the tail of the word,
as a function: the second byte of `в`, `и`, `е` is at least `0xA0`, while
that of `п`, `р`, `с`, `т` is not. Prism.js colors the whole word. The Go
port on the shipped file colors nothing there, since it matches runes and
`\xA0-\xFF` does not contain Cyrillic.

**Nine languages are left out by hand.** The generator's `unsupported`
list (`generate.js:279`) drops `bsl` (1C:Enterprise), `kumir` (КуМир),
`gherkin`, `sparql`, `turtle`, `coq`, `jexl`, `pure` and `purescript`.
Some of them, such as `bsl`, need Cyrillic ranges (`\u0400-\u0484`) that
a byte matcher cannot read. The generator also adds Telegram's own
languages, which Prism lacks: TypeLanguage (`tl`), TL-B, Fift, FunC, Tact
and Tolk.

**Our own grammars.** Generated by the same `generate.js` with both
workarounds removed (keep `\uFFFF`, empty `unsupported`): 4,043 patterns,
957 grammars, 404 names, 663,696 bytes. All compile with regexp2 v1.12.0,
in 81 ms. With them the Go port matches Prism.js on:

- all seven non-ASCII samples, JavaScript included;
- all 76 tests of the nine restored languages, 1C and КуМир included;
- 2,559 of the 2,574 tests in all.

What remains:

- **BQN's characters outside the BMP** (`𝕨`, `𝕩`). The generator writes
  them as UTF-16 surrogate pairs, which a rune matcher cannot match; a
  generator that writes them as one code point would fix this.
- **Two Stata tests**, lost in generation like the ASCII ones.

**Reproducibility.** The generator needs Prism.js itself, so it is
JavaScript. Under Node 18 it reproduced the shipped `grammars.dat` byte for
byte. Under bun 1.4.0, 35 patterns differ only in the case of hex digits
in `\u` escapes (`\u03bb` against `\u03BB`), which means the same thing.

**Limits hold.** All 5,000 hostile cases were run on our grammars with
50 ms per match and 250 ms per block. The worst block took 385 ms, and 14
blocks reached the deadline. regexp2 checks its timeout on a coarse clock,
so a block overshoots the deadline by up to about 135 ms.

**Memory,** Go heap after a GC:

- the loaded `grammars.dat`: 1.4 MB;
- after highlighting 8 common languages: 2.7 MB;
- every one of the 4,043 patterns compiled: 12 MB.

Compiling stays lazy, by language, and the patterns of languages unused
for a while can be dropped.

### Recommendation

**Port libprisma's tokenizer to Go**, on `grammars.dat` and
`dlclark/regexp2`:

- It gives tdesktop's tokens: byte-for-byte the same on 17 files of 9
  languages, on every ASCII input of Prism's test suite, and on the
  hostile cases where both stop a runaway match.
- It is pure Go: about 0.9 MB, nothing to build in C, the same on every
  platform.
- It can be stopped. Use `MatchTimeout` per regex (50 ms measured) and a
  deadline per block (250 ms measured), checked between regex calls. Run
  it on a worker goroutine with tdesktop's LRU cache. If a block is
  stopped, keep the colors found so far, or show it plain.
- It is ours to improve. Map a token's alias when its type has no color,
  and add an alias table (`c++`, `c#`, `golang`…). Both are small
  departures from tdesktop, worth making.
- Ship our own `grammars.dat`, generated without the two workarounds. It
  keeps the ASCII output identical to tdesktop's. It colors non-ASCII code
  as Prism.js does, where tdesktop colors parts of words. And it adds 1C,
  КуМир and seven other languages.
  - Updating it means running the generator from `desktop-app/libprisma`
    with those two changes. That is a Node or bun script, run by hand like
    the wasm build scripts, with its output committed. Agreed
    (2026-10-04): it may live in the repository as a script. Tools in
    `cmd` are Go so that scripts run often stay portable to Windows, and
    this one runs rarely.
  - The file can be embedded gzipped (about 200 KB instead of 664 KB).

**Decided (2026-10-04): regexp2 v1.12.0.** The comparison that led to it:
v1 compiles patterns 24 times faster, so the first
block of a language is quicker, and it adds 0.47 MB less. v2 is the
newer major version (v1.12.0 came out in April 2026, v2.8.2 two days
ago), and it ran a little faster on several inputs. Both gave the
same tokens.

**Colors:** tdesktop's 8 classes, with Android's 7 named groups as a guide
for theme keys (keyword, operator, constant, string, number, comment,
function, plus punctuation or class names). Define them in KomaruGram's
theme for light and dark, not from the chart palette.

The wasm build of libprisma is the closest copy of tdesktop. But it is
fast only without exceptions, a trap then loses a whole block, and a long
block cannot be stopped cheaply. chroma is not hurt by the cases that
break Prism's grammars (the `aaaa…` and `neofetch` inputs), and it knows the
most names. But on the whole hostile set its tail is like libprisma's (63
cases over 5 s, mostly Java and YAML) and its median is higher. It also
colors differently from Telegram and adds 3.3 MB. tree-sitter is too
large and needs a dynamic linker.

## Reproducing

Run everything outside the repository, in a scratch directory and a scratch
copy of the module. Do not add these modules to `go.mod`.

Hostile Markdown inputs:

```python
n = 200000
open('brackets.md', 'w').write('[' * n + 'a' + ']' * n)
open('emph.md', 'w').write('*a **a ' * (n // 2))
open('quotes.md', 'w').write(''.join('> ' * i + 'x\n' for i in range(1, 2000)))
open('lists.md', 'w').write(''.join('  ' * i + '- x\n' for i in range(0, 1500)))
open('table.md', 'w').write('|' + 'a|' * 1000 + '\n|' + '-|' * 1000 + '\n' + ('|' + 'b|' * 1000 + '\n') * 2000)
open('links.md', 'w').write('[a](<' * n)
open('backticks.md', 'w').write(''.join('`' * i + 'a' for i in range(1, 3000)))
open('angle.md', 'w').write('<a ' * n)
open('refs.md', 'w').write(''.join('[%d]: /u%d\n' % (i, i) for i in range(50000)) + ''.join('[x][%d] ' % i for i in range(50000)))
open('footnotes.md', 'w').write(''.join('t[^%d] ' % i for i in range(50000)) + '\n\n' + ''.join('[^%d]: d\n' % i for i in range(50000)))
```

cmark-gfm natively:

```sh
cmake -S cmark-gfm -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMARK_TESTS=OFF
ninja -C build
build/src/cmark-gfm -e table -e strikethrough -e autolink -e tagfilter -e tasklist \
  --strikethrough-double-tilde -t xml input.md
```

cmark-gfm as wasm. Build it natively first, for the generated headers.
`RESOURCE_DIR` is as in `pkg/vp9/build/build.sh`.

```sh
clang-22 --target=wasm32-wasip1 --sysroot=$WASI_SYSROOT -resource-dir $RESOURCE_DIR \
  -O2 -mexec-model=reactor -Wl,--strip-all \
  -Isrc -Iextensions -Ibuild/src -Ibuild/extensions \
  -DCMARK_GFM_STATIC_DEFINE -DCMARK_GFM_EXTENSIONS_STATIC_DEFINE \
  shim.c $(ls src/*.c | grep -v main.c) extensions/*.c -o cmark.wasm
```

MicroTeX as wasm (exceptions in the new encoding):

```sh
CXX="clang++-22 --target=wasm32-wasip1 --sysroot=$WASI_SYSROOT -resource-dir $RESOURCE_DIR \
  -nostdinc++ -isystem $WASI_SYSROOT/include/wasm32-wasip1/eh/c++/v1 \
  -std=c++17 -O2 -fwasm-exceptions -mllvm -wasm-use-legacy-eh=false -Isrc"
# compile src/**/*.cpp except platform/ and samples/, plus a shim and the
# three host functions, then:
clang++-22 --target=wasm32-wasip1 --sysroot=$WASI_SYSROOT -resource-dir $RESOURCE_DIR \
  -fwasm-exceptions -mexec-model=reactor -nostdlib++ \
  -L$WASI_SYSROOT/lib/wasm32-wasip1/eh -lc++ -lc++abi -lunwind \
  -Wl,--gc-sections -Wl,--strip-all *.o -o microtex.wasm
```

Run it with
`wazero.NewRuntimeConfigInterpreter().WithCoreFeatures(api.CoreFeaturesV2 | experimental.CoreFeaturesExceptionHandling)`.

Hostile highlighting inputs: 50 fragments, each written as itself, followed
by `a`, preceded by `a` and followed by a space, repeated to 20,000 bytes,
for each of 25 languages:

```python
langs = ['c', 'cpp', 'csharp', 'go', 'java', 'javascript', 'typescript', 'python', 'ruby', 'rust', 'php', 'bash', 'sql', 'json', 'yaml', 'markup', 'css', 'kotlin', 'swift', 'lua', 'perl', 'haskell', 'scala', 'markdown', 'latex']
seeds = ['a', ' ', '"', "'", '\\', '/*', '//', '<', '<a ', '{', '(', '$(', '${', '#', '-', '=', '.', '0', '\n', '`', "'''", '"""', '<<EOF\n', '/', '*', '@', ':', '[', 'a ', '0x', '1e', '\\"', '"a', '</', '<!--', '-->', '=>', '::', '#{', '%', '&', '|', '~', '!', '?', 'a.', 'a(', 'a<', '\t', ';']
i = 0
for s in seeds:
    for v in (s, s + 'a', 'a' + s, s + ' '):
        open('in/%03d.txt' % i, 'w').write((v * (20000 // len(v) + 1))[:20000])
        i += 1
```

libprisma natively, for reference output. Boost.Regex 1.92 is header-only:

```sh
clang++-22 -std=c++17 -O2 -Ilibprisma -Iregex-boost-1.92.0/include \
  libprisma/*.cpp cli.cpp -o prisma-native
```

`cli.cpp` loads `grammars.dat`, tokenizes a file, and writes each text run's
innermost type and byte length; the Go port's `flatten` writes the same.
libprisma as wasm without exceptions: compile with
`-fno-exceptions -DBOOST_REGEX_STANDALONE`, against
`$WASI_SYSROOT/include/wasm32-wasip1/noeh/c++/v1`, with a forced include
that defines `try` as `if (true)`, `catch(...)` as `if (false)` and `throw`
as `::abort(),`, after replacing Boost's `throw;` with `::abort();`. That
is enough to measure, not to ship.


RaTeX as wasm. Install Rust into a scratch directory, so that nothing
lands in `~/.cargo`:

```sh
export RUSTUP_HOME=$SCRATCH/rustup CARGO_HOME=$SCRATCH/cargo
sh rustup-init.sh -y --no-modify-path --profile minimal --target wasm32-wasip1
```

A `cdylib` crate depends on `ratex-parser`, `ratex-layout` and
`ratex-types` by path, and exports `rt_alloc`, `rt_free`, `rt_layout` and
`rt_out_len`. `rt_layout` calls `parse`, then `layout` with
`LayoutOptions::default().with_style(MathStyle::Display)`, then
`to_display_list`, and serializes the result with `serde_json`. Build it
with `cargo build --release --target wasm32-wasip1`, with RaTeX's release
profile. Run it with `wazero.NewRuntimeConfigCompiler()`: no experimental
features are needed.
