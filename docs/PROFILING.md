# Профилировщик messenger

```sh
go run ./cmd/messenger -demo -profile
go run ./cmd/messenger -profile
go run ./cmd/messenger -profile -profile-dir ./profiles/regression-01
```

`-profile` открывает отдельное окно и включает сбор данных во всех окнах messenger.
Без флага коллектор, sampler и RPC middleware не запускаются. В горячем UI-пути
остаются проверки выключенного режима; отдельной перерисовки ради метрик нет.
`-check` и `-profile` несовместимы.

Закрытие окна профилировщика отключает сбор, останавливает sampler и завершает
активный CPU/trace capture с сохранением файла. Остальные окна продолжают работать.
Если закрыть messenger первым, профилировщик остаётся открытым для просмотра данных;
процесс завершается после закрытия последнего окна.

## Кадры

- Фактический FPS по каждому окну за последние 2 секунды; в покое он падает до нуля.
  Это нормально для Gio: окно не должно рисовать 60 кадров без изменений.
- CPU/frame: setup/theme, Update, Layout и вызов Frame (submit/wait).
- p50/p95/p99, число кадров дольше 16,7 мс, график последних 180 кадров
  (вертикальная шкала 0–50 мс, белая линия — бюджет 60 Hz).
- Вложенные интервалы chat-list, history.total, snapshot+albums, rows, rich-text,
  media и чтение кеша измерений. Они **перекрываются**, складывать их нельзя.
- Размер окна и масштабы DPI/текста сохраняются в JSON.

GPU-время отдельно не измеряется. `submit/wait` — время CPU вокруг `Frame`, которое
может включать ожидания; это не чистая длительность GPU. Окно профилировщика не
включается в FPS/тайминги окон, но его работа входит в память и CPU всего процесса.

## Память

Раз в секунду читаются Go heap/in-use/idle/released, число объектов/goroutines,
скорость аллокаций, количество GC и их паузы. `Sys` — память Go runtime, **не RSS**;
внешние процессы ffmpeg/mpv/VLC и GPU память сюда не входят. HeapAlloc включает ещё
не собранный мусор: удерживаемую память следует оценивать по heap profile после GC.
Профилировщик не запускает принудительную GC и не меняет GC-настройки приложения.

Отдельно показываются количества открытых историй, загруженных сообщений, peer/ref
registry, состояний строк, текстур, кадров медиа и аватаров. Размер декодированных
пикселей — оценка; общие кадры могут учитываться в нескольких местах, память кодеков
в неё не входит. `n/a` означает, что доступно количество, но размер не измерен.
Счётчики store обновляются при завершении страницы; UI-кеши — на кадре раз в секунду.

Кнопки Heap, Allocations и Goroutines сохраняют стандартные `.pprof` файлы:

```sh
go tool pprof -top profiles/<timestamp>-heap.pprof
go tool pprof -sample_index=inuse_space profiles/<timestamp>-heap.pprof
go tool pprof -sample_index=alloc_space profiles/<timestamp>-allocs.pprof
```

Так можно выяснить, какие стеки аллокаций удерживают память. Встроенный список кешей
не является обходом всех Go-объектов и не заменяет heap profile.

## Telegram RPC

Журнал включает приложение → Telegram API, дополнительные media DC-пулы и CDN:
метод, анонимный номер аккаунта, DC, время начала/длительность, TL-байты запроса и
ответа, число сериализаций, статус. Текущие незавершённые вызовы видны отдельно.
Есть текстовый фильтр и переключатель «Только ошибки RPC».

Размер измеряется на **реальных** Encode/Decode, без повторной сериализации ради
статистики. Это TL payload, не размер TCP-пакетов: без MTProto headers, шифрования,
padding, сжатия и транспортных повторов. Ошибка до decoder даёт `?` для размера
ответа, а не ложный ноль. `encodes` — число вызовов Encode, не счётчик сетевых retries.
DC основного клиента указан на момент его создания; после внутренней миграции gotd
он может отличаться. Дополнительные пулы помечаются выбранным DC.

Не перехватываются MTProto ping/ack, handshake и внутренние операции gotd, обходящие
публичные invoker/middleware. Unsolicited updates не являются RPC-ответами: время их
применения видно в событиях `updates.apply`, но их сетевой размер не измеряется.

Журнал не хранит тела запросов/ответов, тексты сообщений, ключи и raw `Error()`.
Ошибки представлены RPC-кодом/типом, cancellation/deadline/network-классом либо Go-типом.
Числовые ChatID/MessageID присутствуют в диагностике истории; экспорт всё равно стоит
считать локальными диагностическими данными.

## История и viewport

Вкладка показывает:

- общее/видимое число сообщений, First/Offset и суммарную высоту;
- число вызовов row layout (включая измерительные проходы Gio), изменённых высот,
  размер кешей строк/измерений и dirty-очереди;
- был ли новый snapshot, rebuild и его причины: width, DPI/text-scale, locale,
  font, theme, renderer, message-count или message-key/content-revision;
- попадания в кеш высот при rebuild, время восстановления anchor и число просмотренных ID;
- время SQLite around/page/layout-read, merge, fetch, записи viewport;
- queued/written/**dropped** для ограниченной очереди SaveView;
- hit/miss медиа-кеша и время загрузки; запросы перерисовки окна и отдельные причины
  history invalidation (ожидающие измерения, спойлер, прокрутка выборки).

Это не полный перехват каждого `op.InvalidateCmd` Gio: внутренние scroll/animation
команды библиотеки не имеют своих reason-тегов. Программа не меняет алгоритмы
истории ради красивых показателей. Сейчас rebuild — O(N), поиск ID при восстановлении
anchor — линейный; HeightIndex использует Fenwick O(log N) для prefix/find.

Для воспроизводимого сценария:

1. Открыть demo или реальный чат и дождаться загрузки.
2. Сбросить метрики, прокрутить вверх, перейти в другой чат и вернуться.
3. На «Истории» проверить restore scan, кеш высот, SQLite timings и отсутствие лишних fetch.
4. Изменить ширину окна/тему, сравнить причины инвалидации и число повторных измерений.
5. При задержке включить CPU на 15 секунд и повторить сценарий. Для ожиданий,
   планировщика и GC использовать Trace на 5 секунд.

```sh
go tool pprof -top profiles/<timestamp>-cpu.pprof
go tool trace profiles/<timestamp>-trace.trace
```

## Сохранение и пределы

«Заморозить вид» удерживает текущий снимок для чтения; фоновый сбор продолжается.
«Сбросить метрики» очищает кадровые/событийные кольца и счётчики; текущие RPC остаются
в работе, последний inventory кешей сохраняется до следующего обновления.
«Экспорт JSON» сохраняет текущие данные коллектора, даже если вид заморожен.

На окно хранятся последние 600 кадров, на процесс — 2048 событий истории, 512
завершённых RPC, до 512 подробностей текущих RPC и 300 отсчётов памяти. Число всех
in-flight RPC учитывается независимо от лимита подробностей. Счётчики overwritten
показывают, когда старые записи вытеснены. JSON содержит schema version и версию Go.

`-profile-export 3s` собирает данные без окна профилировщика и каждые 3 секунды
перезаписывает `latest.json` в новом каталоге `run-<время>-…` внутри `-profile-dir`.
Так меряют длинные сценарии снаружи, например циклы «закрыть в трей → открыть»:
скрипт читает из последнего отсчёта `Memory` поля `HeapInuse`, `HeapObjects` и
`Goroutines`, а RSS берёт из `/proc/<pid>/smaps_rollup`.

Кроме этого файлы создаются только по кнопке: каталог 0700, новые файлы 0600, без перезаписи.
HTTP/pprof-порт не открывается. CPU/trace работают для всего процесса; одновременно
записывается один artifact. Они добавляют измерительную нагрузку, поэтому для сравнения
регрессий следует использовать одинаковый набор включённых инструментов.

Код: `internal/diagnostics`, `internal/profilerui`; точки интеграции находятся в
`internal/appwindow`, account/tgstore/UI и `pkg/dcpool`.
